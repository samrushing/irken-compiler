With so many possible approaches, we need shorthand names for them.

Naming the Approaches
---------------------

    * Pure-VM
      this approach uses only the VM.  The compiler/runtime are all present
      in a single .byc image.

    * Hybrid-VM
      A pre-compiled system hosts/loads the repl environment and runs it in
      the VM.

    * JIT
      perhaps an entry point for a 'real' code generator?  The compiler emits
      closures that can interact with the pre-compiled system.  So for example,
      a call to list:cons references the closure stored at top-level within
      the pre-compiled system.

Using a compiler continuation?
------------------------------

A bit of a crazy idea here... let's say you accept one line of input code at
a time.  You compile that, run it, and generate a result or environment.  Then
the next line comes in.  The simplest thing to do is to recompile all the previous
lines along with the new line, run it, etc.  But what if there was a way to capture
the continuation of the compiler after the last line, and simply 'add on' the next
line? (continue as if it was always there...)

I think this could only work with a completely different compiler design, one that
was streaming all the way through.  Even then I'm not sure it could be done, at
least with Irken, because it's a many-pass compiler.

No, I think the only way to approach this is the compile-to-a-typed-environment
method.

Field Offset Table
------------------

A problem is created by the global field offset table.  If we want to compile
multiple code objects separately, we either need different field offset tables
or we need to merge them all into one.  NOTE pretty sure we have to merge them
at every step (like dynamic linking), because otherwise we will be unable to
safely access structs created in earlier code blocks?

In general we need to think about 'code objects' and the ability to load them
into the VM heap.

[this same problem may arise with symbols]


Code Objects
------------

The current bytecode compiler generates:

    * literals:
        * all literals
        * field lookup table
        * sizeoff index
        * sizeoff literal (needed for FFI i.e. malloc/halloc/c-aref/c-sref)
        * metadata index
    * bytecode (stream of integers)


'Embedded' VM
-------------

Can we have an 'embedded' VM inside a C/LLVM-compiled image?  This might make
a repl easier (among other advantages).

By 'embedded' I mean a VM that uses the same heap as the hosting image.  The bytecode
compiler is there as well.  This is close to how CPython works.

So rather than having the VM be a standalone program, it's an almost-FFI-like
entry point that evaluates its bytecode and then returns some object.  It's
possible that we could even pass the bytecode in as a legal Irken object (i.e. a
vector of ints).

What would be super cool is if we could have the bytecode compiler reference
closures in the hosting image?  e.g. tree/insert, string->symbol etc.

I think this would be possible if we could preserve the type information from
the hosting image - at least the top-level objects?

This is much more like a JIT though.

How to approach thinking about this.  Maybe step ONE is to get 'multiple code objects'
working, as in a chain of code objects each referencing the previous env.

If we figure that out (completely as bytecode) then perhaps we can then extend that to
reference the hosting environment.  In this case we share only the heap.  Actually, this
means we need to add to the root set anything meant to be preserved?  I guess storing the
result of the FFI call may be enough?  [I think using the registers as roots would cause
leaks, since those objects are no longer live].
